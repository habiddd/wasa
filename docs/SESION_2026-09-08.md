# Cambios en la sesión del 8 de septiembre de 2026

## Resumen

Seguimiento sobre el dashboard interno (`/dashboard`, ver
`docs/SESION_2026-09-04.md` para el contexto de las pestañas "Activos" y
"Lugares" agregadas la sesión anterior). Dos pedidos explícitos, en dos
vueltas:

1. Una pestaña nueva para ver los usuarios registrados por el bot de
   WhatsApp, con datos de prueba para poder verla poblada.
2. Un botón para poder editar los atributos de cada usuario desde ahí mismo.

## 1. Pestaña nueva: "Usuarios"

**Backend** (`flask-app/app/routes/dashboard.py`): `GET /dashboard/api/usuarios`
devuelve `Usuario.query.filter_by(registro_completo=True)`, ordenados por
`creado_en` descendente. El filtro por `registro_completo=True` no fue una
ocurrencia aparte -- es justo el criterio que el usuario pidió ("solo debe
estar el que yo creé"): de las dos filas que había en `usuarios` antes de
esta sesión, la real (`Habid abdala`, creada por el flujo de WhatsApp) tiene
`registro_completo=True`, y la de `seed.py` (`Usuario de Pruebas`, dummy para
poder probar reservas) tiene `registro_completo=False` porque nunca pasó por
el flujo de registro real -- así que el mismo filtro que pide "solo
usuarios reales del bot" excluye la fila dummy sin necesidad de un caso
especial por nombre/teléfono.

**Frontend** (`flask-app/app/templates/dashboard.html`): pestaña nueva
`#usuarios` con una tabla (nombre, teléfono, código Uninorte, cédula, rol,
activo, fecha de registro). Se carga junto con Servicios/QR/Métricas al
abrir la página y se refresca sola cada 30s (`setInterval(cargarUsuarios,
30000)`), más un botón "Refrescar" manual.

**Datos de prueba**: como `postgres/init/*.sql` y `seed.py` solo corren la
primera vez que se crea el volumen (mismo patrón que otras sesiones, ver
`docs/SESION_2026-08-31.md` sección 3), no bastaba con tocar `seed.py` para
que aparecieran usuarios nuevos en la base real ya inicializada. Se
insertaron dos usuarios de prueba directo contra `cpa_postgres`
(`Maria Fernanda Rojas`, `Carlos Andres Perez`, ambos con
`registro_completo=true` y un `telefono_wa`/`codigo_uninorte`/`cedula`
inventados pero con formato realista) para que la pestaña tuviera algo más
que la fila real del usuario al abrirla. No es un archivo del repo, pero es
parte de lo que cambió hoy (igual que la migración `activo` -> `estado` de
la sesión anterior).

## 2. Botón "Editar" por usuario

**Backend**: `PATCH /dashboard/api/usuarios/<id>`, mismo patrón que ya existe
para activos (`_CAMPOS_EDITABLES_ACTIVO`/`api_actualizar_activo`):

- `_CAMPOS_EDITABLES_USUARIO` rechaza explícitamente cualquier campo del
  body que no sea `nombre`, `telefono_wa`, `codigo_uninorte`, `cedula`, `rol`
  o `activo` -- en particular, **no** se puede tocar `registro_completo`
  desde el dashboard (ese lo controla el flujo de WhatsApp, no un admin
  editando a mano).
- `_ROLES_VALIDOS = {"estudiante", "staff", "admin"}` valida `rol` en Python
  antes de tocar la fila (no hay `CHECK` de Postgres para esta columna --
  ver comentario en `postgres/init/02-schema.sql` línea 23 -- así que sin
  esta validación cualquier string pasaría).
- `telefono_wa` vacío se rechaza explícitamente (es la única columna
  `NOT NULL` del grupo editable); un teléfono duplicado se atrapa como
  `IntegrityError` (la tabla tiene `UNIQUE` en `telefono_wa`) y se traduce a
  un mensaje en español en vez de exponer el error crudo de psycopg -- mismo
  criterio que `_mensaje_integridad` para activos, aunque acá solo hay un
  caso posible así que no hizo falta un diccionario completo.

**Frontend**: cada fila de la tabla tiene un botón "Editar" que despliega,
en una fila propia debajo (`<tr class="fila-form-usuario">`), un formulario
inline con los mismos campos editables del backend -- reutiliza la clase
`form.form-activo` (estilos ya existentes de la sesión anterior) en vez de
CSS nuevo. Guardar hace `PATCH` y recarga la tabla; Cancelar cierra el
formulario sin guardar. Igual que con las tarjetas de Activos, abrir el
formulario de una fila cierra cualquier otro que estuviera abierto, para no
dejar ediciones a medias en paralelo.

## Cómo se probó

Mismas limitaciones que la sesión anterior (Windows, sin `python` en el
`PATH` fuera de Docker, sin navegador headless disponible):

1. **Stack real**: cambios en `dashboard.py`/`dashboard.html` solo llegan al
   contenedor reconstruyendo la imagen (`docker compose build flask-app &&
   docker compose up -d flask-app`) -- no hay bind mount, `COPY . .` en el
   `Dockerfile` la deja fija en la imagen. Se reconstruyó dos veces, una por
   cada pedido de esta sesión.
2. **`GET /dashboard/api/usuarios`**, con `curl` autenticado (Basic Auth
   real contra `DASHBOARD_USER`/`DASHBOARD_PASSWORD` del contenedor):
   confirmado que devuelve exactamente los 3 usuarios con
   `registro_completo=true` (el real + los 2 de prueba) y **no** la fila
   dummy de `seed.py`.
3. **`PATCH /dashboard/api/usuarios/<id>`**, con `curl`: edición válida
   (nombre + rol) devuelve `200` con la fila actualizada; campo no editable
   (`registro_completo`) devuelve `400`; rol inválido (`"superadmin"`)
   devuelve `400` con el mensaje de roles válidos; teléfono duplicado
   (el de otro usuario existente) devuelve `400` con "Ya existe otro usuario
   con ese teléfono". El cambio de prueba (nombre/rol) se revirtió al
   terminar para no dejar datos de QA en la fila real.
4. **HTML servido**: se confirmó con `curl` + `grep` que el tab
   `data-tab="usuarios"` y el botón `editar-usuario` aparecen en la página
   tal como la sirve el contenedor reconstruido (no solo en el archivo en
   disco).

**Limitación reconocida** (igual que la sesión anterior): sin verificación
visual real en navegador -- no se abrió el formulario inline con un clic
físico ni se tomó captura de pantalla, solo se confirmó backend real +
presencia del HTML/JS servido. Si el layout de la fila de formulario dentro
de la tabla (`<tr><td colspan="8">...`) se ve raro en el navegador real, no
quedó cubierto por esta verificación.
