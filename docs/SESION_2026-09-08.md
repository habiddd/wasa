# Cambios en la sesión del 8 de septiembre de 2026

## Resumen

Seguimiento sobre el dashboard interno (`/dashboard`, ver
`docs/SESION_2026-09-04.md` para el contexto de las pestañas "Activos" y
"Lugares" agregadas la sesión anterior). Ocho pedidos explícitos, en ocho
vueltas:

1. Una pestaña nueva para ver los usuarios registrados por el bot de
   WhatsApp, con datos de prueba para poder verla poblada.
2. Un botón para poder editar los atributos de cada usuario desde ahí mismo.
3. Reemplazar toda la UI del dashboard (hasta ahora HTML/CSS/JS vanilla
   servido por Jinja) por componentes reales de
   [shadcn/ui](https://ui.shadcn.com/), con selector de tema claro/oscuro,
   manteniendo exactamente la misma funcionalidad de las seis pestañas.
4. Cambiar las seis pestañas horizontales por un panel de navegación
   vertical a la izquierda.
5. Separar ese frontend en su propio contenedor Docker (hasta ese momento
   se compilaba dentro de la imagen de `flask-app`) -- pedido explícito de
   "buena práctica" tras notar procesos `node.exe` corriendo en Windows
   durante la verificación visual del punto 4.
6. Convertir ese panel vertical en un sidebar de verdad: fijo (no se mueve
   con el scroll de la página), colapsable, y con texto más grande.
7. Unir la pestaña "QR / WhatsApp" dentro de "Servicios", como una
   sub-pestaña más en vez de una entrada propia del sidebar.
8. Agregar, dentro de "Usuarios", una sub-pestaña "Sesiones" con la misma
   metodología que la sub-pestaña de QR dentro de Servicios (punto 7): las
   sesiones de uso (reservas) de cada persona, organizables por usuario o
   por más reciente, y filtrables por categoría (el campo `rol`).

## 1. Pestaña nueva: "Usuarios"

**Backend** (`flask-app/app/routes/dashboard.py`): `GET /dashboard/api/usuarios`
devuelve `Usuario.query.filter_by(registro_completo=True)`, ordenados por
`creado_en` descendente. El filtro por `registro_completo=True` no fue una
ocurrencia aparte -- es justo el criterio que el usuario pidió ("solo debe
estar el que yo creé"): de las dos filas que había en `usuarios` antes de
esta sesión, la real (`Habid abdala`, creada por el flujo de WhatsApp) tiene
`registro_completo=True`, y la de `seed.py` (`Usuario de Pruebas`, dummy para
poder probar reservas) tiene `registro_completo=False` porque nunca pasó por
el flujo de registro real -- así que el mismo filtro que pide "solo
usuarios reales del bot" excluye la fila dummy sin necesidad de un caso
especial por nombre/teléfono.

**Frontend** (`flask-app/app/templates/dashboard.html`): pestaña nueva
`#usuarios` con una tabla (nombre, teléfono, código Uninorte, cédula, rol,
activo, fecha de registro). Se carga junto con Servicios/QR/Métricas al
abrir la página y se refresca sola cada 30s (`setInterval(cargarUsuarios,
30000)`), más un botón "Refrescar" manual.

**Datos de prueba**: como `postgres/init/*.sql` y `seed.py` solo corren la
primera vez que se crea el volumen (mismo patrón que otras sesiones, ver
`docs/SESION_2026-08-31.md` sección 3), no bastaba con tocar `seed.py` para
que aparecieran usuarios nuevos en la base real ya inicializada. Se
insertaron dos usuarios de prueba directo contra `cpa_postgres`
(`Maria Fernanda Rojas`, `Carlos Andres Perez`, ambos con
`registro_completo=true` y un `telefono_wa`/`codigo_uninorte`/`cedula`
inventados pero con formato realista) para que la pestaña tuviera algo más
que la fila real del usuario al abrirla. No es un archivo del repo, pero es
parte de lo que cambió hoy (igual que la migración `activo` -> `estado` de
la sesión anterior).

## 2. Botón "Editar" por usuario

**Backend**: `PATCH /dashboard/api/usuarios/<id>`, mismo patrón que ya existe
para activos (`_CAMPOS_EDITABLES_ACTIVO`/`api_actualizar_activo`):

- `_CAMPOS_EDITABLES_USUARIO` rechaza explícitamente cualquier campo del
  body que no sea `nombre`, `telefono_wa`, `codigo_uninorte`, `cedula`, `rol`
  o `activo` -- en particular, **no** se puede tocar `registro_completo`
  desde el dashboard (ese lo controla el flujo de WhatsApp, no un admin
  editando a mano).
- `_ROLES_VALIDOS = {"estudiante", "staff", "admin"}` valida `rol` en Python
  antes de tocar la fila (no hay `CHECK` de Postgres para esta columna --
  ver comentario en `postgres/init/02-schema.sql` línea 23 -- así que sin
  esta validación cualquier string pasaría).
- `telefono_wa` vacío se rechaza explícitamente (es la única columna
  `NOT NULL` del grupo editable); un teléfono duplicado se atrapa como
  `IntegrityError` (la tabla tiene `UNIQUE` en `telefono_wa`) y se traduce a
  un mensaje en español en vez de exponer el error crudo de psycopg -- mismo
  criterio que `_mensaje_integridad` para activos, aunque acá solo hay un
  caso posible así que no hizo falta un diccionario completo.

**Frontend**: cada fila de la tabla tiene un botón "Editar" que despliega,
en una fila propia debajo (`<tr class="fila-form-usuario">`), un formulario
inline con los mismos campos editables del backend -- reutiliza la clase
`form.form-activo` (estilos ya existentes de la sesión anterior) en vez de
CSS nuevo. Guardar hace `PATCH` y recarga la tabla; Cancelar cierra el
formulario sin guardar. Igual que con las tarjetas de Activos, abrir el
formulario de una fila cierra cualquier otro que estuviera abierto, para no
dejar ediciones a medias en paralelo.

## 3. Migración completa de la UI del dashboard a React + shadcn/ui

**Pedido explícito:** usar [shadcn/ui](https://ui.shadcn.com/docs/) para la
UI del dashboard, migrando "los mismos componentes" (es decir, sin perder
ninguna de las seis pestañas ni su funcionalidad) a esta nueva librería, con
selector de tema claro/oscuro.

**Por qué no fue un simple restyle de CSS.** shadcn/ui no es una hoja de
estilos: son componentes de **React** sobre Tailwind + Radix UI, pensados
para un proyecto con bundler (Vite/Next). El dashboard hasta ahora era
`flask-app/app/templates/dashboard.html`, un único archivo HTML/CSS/JS
vanilla renderizado por Jinja, sin Node ni build step de ningún tipo en
`flask-app/`. Antes de tocar código se le presentó la disyuntiva al
usuario -- migración real a React (nuevo toolchain Node en el repo, Flask
pasa a servir un build estático) vs. quedarse en Jinja/vanilla imitando
solo la estética de shadcn -- y confirmó que quería la migración real.

**Proyecto nuevo:** `flask-app/dashboard-frontend/` (Vite + React 19 + TS +
Tailwind v4 vía `@tailwindcss/vite` + shadcn/ui, preset "Nova" con Radix UI
e iconos `lucide-react`). Estructura por feature, calcando 1:1 la lógica que
ya existía en `dashboard.html`:

- `src/lib/api.ts` -- wrapper de `fetch` + tipos TS para los 8 endpoints de
  `/dashboard/api/*` (ninguno cambió de contrato; el backend no se tocó más
  que en cómo sirve el HTML, ver abajo).
- `src/components/theme-provider.tsx`/`theme-toggle.tsx` -- selector de tema
  claro/oscuro/sistema. No se usó `next-themes` (es específico de Next.js);
  es un `ThemeProvider` propio con contexto de React + `localStorage`, clase
  `dark` en `<html>`, siguiendo el patrón que la propia documentación de
  shadcn recomienda para proyectos Vite.
- `src/features/servicios|qr|metricas/*Panel.tsx` -- mismos tres paneles de
  antes (grid de `Card`, imagen QR, tabla de interacciones), mismos
  intervalos de refresco (10s/5s/30s) vía un hook genérico
  (`src/hooks/use-polling.ts`).
- `src/features/usuarios/*` -- tabla + fila de edición inline, mismo patrón
  que la sección 2 de esta sesión, ahora con `Input`/`Select`/`Checkbox` de
  shadcn en vez de HTML plano.
- `src/features/activos/*` -- la parte más compleja de portar: árbol
  recursivo padre/hijo, subpestañas por categoría, selector de estado
  inline, formularios de crear/editar. Para que "Activos" y "Lugares"
  sigan compartiendo una sola caché de datos (como `activosCache`, una
  variable a nivel de módulo en el script original), se armó
  `activos-context.tsx`: un `ActivosProvider` de React que envuelve ambas
  pestañas y no se desmonta al cambiar de tab, con el mismo criterio de
  recarga que antes (se refresca al entrar a cualquiera de las dos, nunca
  solo -- botón "Refrescar" manual) y los mismos `Set` de ids
  expandidos/subpestaña activa persistidos en `localStorage`.
- Errores de guardar un activo (antes `alert()` del navegador) ahora se
  muestran con `sonner` (el componente de notificaciones de shadcn) -- igual
  contenido, mejor presentación; en Usuarios se mantuvo el error inline en
  el propio formulario, igual que antes, porque ahí nunca fue un `alert()`.

**Backend** (`flask-app/app/routes/dashboard.py`): `index()` deja de usar
`render_template` -- sirve `app/dashboard_dist/index.html` (el build de
Vite) con `send_from_directory`; ruta nueva `GET /dashboard/assets/<...>`
para los JS/CSS con hash. Ambas quedan cubiertas por el mismo
`before_request` de Basic Auth que ya protegía todo el blueprint, sin
excepciones nuevas. `flask-app/app/templates/dashboard.html` se eliminó
(reemplazado, no quedó como fallback). Ningún endpoint `/dashboard/api/*`
cambió de firma ni de comportamiento.

**Build/Docker:** `flask-app/Dockerfile` pasa a **multi-stage** -- un stage
`node:20-slim` corre `npm ci && npm run build` sobre
`dashboard-frontend/` y el stage Python final copia el `dist/` resultante a
`app/dashboard_dist/`. Antes de este cambio, construir la imagen de
`flask-app` no requería Node en absoluto; ahora sí, aunque solo dentro del
build de la imagen (el contenedor final sigue siendo solo Python). Se
agregó `flask-app/.dockerignore` para no arrastrar `node_modules/` al
contexto de build del stage Python, y se actualizó el `.gitignore` raíz
(`dashboard-frontend/node_modules/`, `dashboard-frontend/dist/`,
`app/dashboard_dist/` -- ninguno de los tres se versiona).

**Bug real encontrado y corregido durante la verificación visual** (no
hipotético -- ver sección "Cómo se probó"): el componente `Table` de
shadcn ya envuelve la tabla en su propio `<div overflow-x-auto>`
internamente; el código agregó **otro** `overflow-x-auto` por fuera, y los
dos contenedores de scroll anidados dejaban el botón "Editar" de la última
columna cortado a la mitad (visible en la captura, no en el build ni en
`curl`). Fix: quitar el `overflow-x-auto` duplicado (dejar solo
`rounded-md border`, que es el patrón que la propia documentación de
shadcn usa) y ensanchar el contenedor principal de `max-w-4xl` a
`max-w-6xl` porque una tabla de 8 columnas con el padding por defecto de
shadcn no entraba cómoda en el ancho original (pensado para el layout más
angosto del HTML viejo).

## 4. Pestañas horizontales -> panel de navegación vertical

**Pedido explícito:** mover las seis pestañas (hasta ahora un `TabsList`
horizontal arriba del contenido, ver captura del pedido) a un panel a la
izquierda.

El componente `Tabs` de shadcn (`flask-app/dashboard-frontend/src/components/
ui/tabs.tsx`) ya soportaba `orientation="vertical"` de fábrica (viene así
del preset "Nova" instalado en la sección 3) -- no hubo que escribir CSS de
layout vertical desde cero, solo usar la prop que no se estaba usando.
Cambios en `src/App.tsx`:

- `<Tabs orientation="vertical" className="flex-row items-start gap-6">`
  en vez del `<Tabs>` por defecto (horizontal).
- `<TabsList className="w-48 shrink-0">` para fijarle un ancho al panel
  (sin esto, el `TabsList` vertical se encoge al ancho del texto más largo
  y no queda alineado como columna).
- El contenido de cada pestaña se envolvió en un `<div className="min-w-0
  flex-1">` para que ocupe el resto del ancho disponible.

`cn` (el paquete usado como `cn()` en este proyecto, ver
`package.json` -- es tailwind-merge + clsx combinados, no un simple
`clsx`) resuelve los conflictos de clases Tailwind por orden de aparición
en la cadena final, así que `className="flex-row items-start gap-6"`
sobrescribe el `flex gap-2` que trae el componente base sin tocar
`tabs.tsx`.

## 5. `dashboard-frontend` pasa a ser su propio contenedor

**Motivo del pedido:** al verificar visualmente el cambio de la sección 4
se levantó `npm run dev` (Vite) directo en Windows para tomar una captura
de pantalla -- válido para verificar un cambio de UI puntual, pero dejó
dos procesos `node.exe` corriendo sueltos en el host (uno no se cerró bien
la primera vez). El usuario los vio en su Windows y pidió explícitamente
que **todo el proyecto viva en Docker, en un solo conjunto de contenedores
orquestados por `docker-compose.yml`**, y que si el dashboard necesitaba
su propio contenedor por buena práctica, se hiciera así en vez de
compilarlo dentro de la imagen de `flask-app` (que es como había quedado
en la sección 3).

**Antes de tocar nada** se confirmó que la arquitectura de la sección 3 ya
era "un solo proyecto" en el sentido de que no había nada corriendo fuera
de Docker en producción -- los `node.exe` eran solo de la verificación
manual de la sección 4, no parte de cómo corre la app. Aun así, tener el
build de Node como *stage* de la imagen de `flask-app` mezclaba dos
responsabilidades en un solo contenedor (backend Python + build de
frontend), así que separarlo en un servicio propio es una mejora real, no
solo cosmética.

**`flask-app/dashboard-frontend/Dockerfile`** (nuevo, multi-stage):

- Stage `build` (`node:20-slim`): `npm ci && npm run build`, igual que
  antes pero corriendo dentro de este proyecto en vez del `Dockerfile` de
  `flask-app`.
- Stage final `nginx:1.27-alpine`: sirve el `dist/` compilado. Se le
  instala `openssl` (`apk add --no-cache openssl`) porque la imagen base
  no lo trae y el entrypoint lo necesita para generar el `.htpasswd` (ver
  abajo) -- esto se descubrió en runtime, no al construir la imagen: el
  build terminaba bien, pero el contenedor entraba en crash-loop porque el
  script de entrypoint fallaba con `openssl: not found` y el
  `docker-entrypoint.sh` de la imagen oficial de Nginx aborta si un script
  de `/docker-entrypoint.d/` falla.

**`flask-app/dashboard-frontend/nginx.conf`** (nuevo): un único `server`
que resuelve dos responsabilidades con dos `location` **hermanas** (no
anidadas -- importante, ver más abajo):

- `location /dashboard/api/` hace `proxy_pass` directo a
  `http://flask-app:5000/dashboard/api/` sobre la red `backend` de
  Compose, reenviando `Host`/`X-Real-IP`/`X-Forwarded-For`/
  `X-Forwarded-Proto`. No tiene `auth_basic` propio.
- `location /dashboard/` sirve los estáticos (`alias
  /usr/share/nginx/html/dashboard/`, `try_files $uri $uri/
  /dashboard/index.html` para que las rutas de la SPA no den 404 al
  recargar) y sí exige `auth_basic` contra un `.htpasswd` generado en el
  arranque del contenedor.

Como las dos `location` son **hermanas** dentro del mismo `server` (no una
anidada dentro de la otra), Nginx no hereda el `auth_basic` de
`/dashboard/` hacia `/dashboard/api/` -- son bloques independientes que
compiten por el prefijo más específico. Eso es intencional: la API sigue
protegida por el `before_request` de `flask-app` (`dashboard.py`,
`_requiere_auth`), que no se tocó, así que las credenciales no quedan
duplicadas en dos formatos distintos (Nginx usa `htpasswd`/`apr1`, Flask
compara el password plano con `secrets.compare_digest`) para el mismo
recurso. Se verificó con `curl` que pedir `/dashboard/api/status` sin
credenciales devuelve `401` con el cuerpo `"Autenticación requerida."`
-- el mensaje literal que arma `dashboard.py`, no la página de error por
defecto de Nginx -- confirmando que el 401 lo emite Flask, no una regla de
auth duplicada en Nginx.

**`flask-app/dashboard-frontend/docker-entrypoint.sh`** (nuevo): se copia a
`/docker-entrypoint.d/40-dashboard-htpasswd.sh` (la imagen oficial de
Nginx ejecuta automáticamente, en orden alfabético, todo script
`*.sh` ejecutable en ese directorio antes de arrancar). Genera
`/etc/nginx/.htpasswd` con `openssl passwd -apr1` a partir de
`DASHBOARD_USER`/`DASHBOARD_PASSWORD` (las mismas variables de entorno que
ya usaba `flask-app`) en cada arranque del contenedor -- no se versiona un
`.htpasswd` estático porque la contraseña vive en `.env`, no en el repo.

**`flask-app/Dockerfile`**: se eliminó el stage `frontend-build` y el
`COPY --from=frontend-build`. Vuelve a ser una imagen 100% Python, como
antes de la sección 3 -- construir `flask-app` ya no requiere Node para
nada (con esto queda resuelto el pendiente que había quedado abierto al
final de la sección 3 sobre este mismo punto).

**`flask-app/app/routes/dashboard.py`**: se borraron las rutas `index()` y
`assets()` (y el import de `Path`/`send_from_directory` que ya no se
usaban) -- ahora las sirve Nginx, no Flask. El blueprint quedó reducido a
solo los endpoints `/dashboard/api/*`; el `before_request` de Basic Auth
sigue cubriendo todo el blueprint igual que antes.

**`docker-compose.yml`**: servicio nuevo `dashboard-frontend`
(`cpa_dashboard_frontend`), build desde
`./flask-app/dashboard-frontend`, publicado en `127.0.0.1:8080:80`,
mismas `DASHBOARD_USER`/`DASHBOARD_PASSWORD` que `flask-app` (para que
Nginx pueda generar su `.htpasswd`), en la misma red `backend`. La URL
pública del dashboard pasa de `http://localhost:5000/dashboard` a
`http://localhost:8080/dashboard`.

**Otros archivos actualizados para que dejen de mencionar el esquema
viejo:** `flask-app/dashboard-frontend/vite.config.ts` (`outDir` pasa de
`../app/dashboard_dist` a `dist`, local al propio proyecto de frontend --
ya no tiene sentido que el build "cruce" hacia `flask-app/app/`),
`flask-app/.dockerignore` (ahora excluye todo `dashboard-frontend/` del
contexto de build de `flask-app`, no solo sus artefactos generados),
`flask-app/dashboard-frontend/.dockerignore` (nuevo, excluye
`node_modules/`/`dist/` del contexto de build de este contenedor),
`README.md` (URL nueva, sección 5 explica el contenedor separado y las dos
capas de autenticación, árbol de archivos), `docs/ARQUITECTURA.md`
(sección "Migración del dashboard a React + shadcn/ui" reescrita para
explicar el contenedor propio, el proxy de Nginx y por qué la
autenticación quedó en dos capas independientes en vez de una sola).

## 6. El panel vertical pasa a ser un sidebar de verdad

Tras ver el panel vertical de la sección 4 en un viewport angosto, el
usuario pidió tres cosas más sobre el mismo panel, en tres vueltas
seguidas: que quedara **pegado a la izquierda e independiente del scroll**
de la página (el `TabsList` de la sección 4 era solo una columna flotando
dentro del `<main>`, no un panel fijo -- al hacer scroll se movía con el
resto del contenido), que se pudiera **esconder**, y que el **texto fuera
más grande** con **menos espacio en blanco** dentro del panel.

**Se descartó seguir extendiendo el `Tabs` vertical de la sección 4** --
lograr posición fija, colapso con animación, versión móvil en overlay y
atajo de teclado a mano habría sido reimplementar (peor) algo que shadcn ya
resuelve como componente propio: `Sidebar`. Se instaló con su CLI
(`npx shadcn@latest add sidebar -y -o`, ya estaba disponible como
dependencia del proyecto desde la sección 3) en vez de escribirlo a mano,
agregando 4 archivos nuevos y actualizando uno:

- `src/components/ui/sidebar.tsx` -- el componente en sí
  (`SidebarProvider`, `Sidebar`, `SidebarTrigger`, `SidebarMenu*`, etc.).
- `src/components/ui/sheet.tsx` y `src/hooks/use-mobile.ts` -- el sidebar
  los usa para mostrarse como panel deslizable superpuesto (`Sheet`) en
  vez de columna fija cuando el viewport es angosto (`useIsMobile`,
  breakpoint md).
- `src/components/ui/tooltip.tsx` -- lo usa `SidebarMenuButton` para
  mostrar el label como tooltip cuando el sidebar está colapsado en modo
  ícono (no se usa ese modo acá, pero es parte del componente).
- `src/components/ui/separator.tsx` -- actualizado por la CLI (ya
  existía desde la sección 3; el sidebar depende de una versión más nueva
  del mismo componente).

Ninguno sumó dependencias nuevas a `package.json` -- todo sobre
`radix-ui`, ya presente. Las variables CSS que el sidebar necesita
(`--sidebar`, `--sidebar-foreground`, `--sidebar-accent`, etc.) ya estaban
en `src/index.css` desde que se inicializó shadcn en la sección 3 (el
preset "Nova" las incluye por defecto aunque no hubiera ningún componente
usándolas todavía), así que no hizo falta tocar el archivo de temas.

**`src/App.tsx` reescrito** para usar el sidebar en vez de `Tabs`:
`SidebarProvider` envuelve todo, `Sidebar collapsible="offcanvas"`
(colapso completo, no a modo ícono -- no había íconos por pestaña) con un
`SidebarMenuButton` por pestaña (`isActive`/`onClick` reemplazan el
`value`/`onValueChange` que tenía `Tabs`), y `SidebarInset` como contenedor
del header + contenido a la derecha. El contenido de la pestaña activa se
resuelve buscando en el array `TABS` (ahora cada entrada lleva también su
componente `Panel`) en vez de un `TabsContent` por pestaña -- mismo
resultado (solo se monta el panel activo), menos código.

La posición fija no requirió CSS propio: el `Sidebar` del preset ya
renderiza su contenedor real con `fixed inset-y-0 ... h-svh` (ver
`sidebar.tsx`), así que queda anclado a la ventana sin importar cuánto
scrollee el `<main>` de al lado -- verificado con una captura antes/después
de hacer `window.scrollBy` sobre la pestaña de Métricas (la única con
contenido suficiente para scrollear). El colapso (botón `SidebarTrigger`
en el header, ícono de panel) y el atajo `Ctrl/Cmd+B` vienen del
componente sin configuración adicional.

**Ajustes de tamaño**, en dos vueltas dentro de esta misma sección:

1. Ancho del panel reducido de `16rem` a `13.5rem`
   (`SIDEBAR_WIDTH` en `sidebar.tsx` -- única constante que hay que tocar,
   no hay que buscarla en varios lugares) y texto de los ítems subido de
   `text-sm` (por defecto del componente) a `text-base`, para achicar el
   espacio en blanco a la derecha de cada label sin perder el ancho
   necesario para "QR / WhatsApp" (el label más largo).
2. El usuario pidió una vez más "un poco más grande": texto subido de
   `text-base` a `text-lg` y alto del botón de `h-8` (default del
   componente) a `h-9` (para que el texto más grande no se vea apretado
   verticalmente), vía `className` en cada `SidebarMenuButton` --
   `cn()` (tailwind-merge) resuelve el conflicto con las clases `h-8
   text-sm` que trae `sidebarMenuButtonVariants` por defecto.

**Bug real encontrado durante la verificación de esta sección** (no en el
sidebar en sí, sino en cómo se lo probó): la primera vez que se levantó el
contenedor `dashboard-frontend` reconstruido, entró en crash-loop porque
`docker-entrypoint.sh` (sección 5) llamaba a `openssl`, que no viene
instalado en `nginx:1.27-alpine`. Se vio en `docker logs` como
`openssl: not found` repetido varias veces seguidas (una por cada reinicio
del contenedor). Fix: `RUN apk add --no-cache openssl` en el
`Dockerfile` del frontend, antes de copiar `nginx.conf`.

## 7. "QR / WhatsApp" pasa a ser una sub-pestaña de "Servicios"

## 8. Sub-pestaña "Sesiones" dentro de "Usuarios"

**Pedido explícito:** dentro de "Usuarios", agregar una sub-pestaña con la
misma metodología que la de QR dentro de Servicios (sección 7) que muestre
las sesiones de cada persona, con su nombre, organizables por usuario y por
más reciente, y filtrables por categoría (el campo que ya distingue
estudiante de otro tipo de usuario).

**Qué es una "sesión" acá.** El proyecto ya tenía dos conceptos distintos
que podían llamarse "sesión": `app/sesiones.py` (memoria de conversación de
WhatsApp en Redis, por número, sin relación con usuarios registrados ni con
nada que tenga sentido listar en una tabla) y el modelo `Reserva`
(`app/models.py`) -- cada reserva de un recurso (cámara, sala, dron...)
tiene `usuario_id`, `inicio`/`fin`, `estado`. Esto último es lo que pedía el
usuario: una "sesión de uso" por persona. Se mantuvo el nombre de módulo
Python `Reserva`/`reservas` sin tocar (es el modelo y la tabla real) y se
usó "Sesiones" solo como la etiqueta de la sub-pestaña y el nombre del
componente de React, para no crear una confusión de nombres con
`app/sesiones.py` en el propio código del backend.

**Backend** (`flask-app/app/routes/dashboard.py`): endpoint nuevo
`GET /dashboard/api/reservas`, mismo patrón que `api_usuarios`/
`api_activos` (una función `_serializar_reserva` + una ruta que arma la
query y devuelve `jsonify`). Trae las reservas con
`.options(joinedload(Reserva.usuario), joinedload(Reserva.recurso))` para no
disparar una query por fila al serializar `usuario.nombre`/`usuario.rol`/
`recurso.nombre` (el patrón que ya usan `usuario`/`recurso` como
`db.relationship` en `models.py`, pero que hasta ahora ningún endpoint del
dashboard leía en forma de listado); `order_by(Reserva.creado_en.desc())` +
`limit(500)` como techo razonable (no se pidió paginación, y una demo/CPA
con cientos de reservas no se acerca a ese límite). El campo `usuario_rol`
del JSON es el mismo `Usuario.rol` que ya se edita desde la pestaña
"Usuarios" (`estudiante`/`staff`/`admin`) -- no se agregó ninguna columna ni
tabla nueva, la "categoría" que pedía el usuario ya existía.

**Frontend:**

- `src/lib/api.ts` -- tipos `EstadoReserva`/`Sesion` y `fetchSesiones()`
  (`GET /reservas`), mismo patrón que el resto del archivo (`request<T>`
  genérico).
- `src/features/usuarios/UsuariosPanel.tsx` -- se envolvió en
  `Tabs`/`TabsList`/`TabsTrigger`/`TabsContent` de shadcn, igual que
  `ServiciosPanel.tsx` en la sección 7: la tabla que antes era todo el panel
  pasó a un sub-componente `ListaUsuariosTab` (sin cambios de lógica, solo
  se le quitó el nombre `UsuariosPanel` porque ahora ese nombre lo tiene el
  wrapper con los tabs) bajo la viñeta "Usuarios", y la viñeta nueva
  "Sesiones" monta `SesionesTab`. `defaultValue="usuarios"` mantiene la
  tabla de usuarios como vista inicial al entrar a la sección, mismo
  criterio que `defaultValue="estado"` en Servicios.
- `src/features/usuarios/SesionesTab.tsx` (nuevo): polling cada 30s
  (`usePolling(fetchSesiones, 30000)`, mismo intervalo que ya usaba
  `UsuariosPanel` para la lista de usuarios). Dos `Select` de shadcn:
  - **Ordenar por** -- "Más reciente" (tabla plana, en el mismo orden que ya
    devuelve el backend por `creado_en` descendente) o "Por usuario"
    (agrupa las sesiones filtradas en un `Map<usuario_id, ...>` con
    `useMemo`, ordena los grupos alfabéticamente por nombre con
    `localeCompare`, y renderiza una `Card` por persona -- nombre en el
    título, `Badge` con su rol al lado, y adentro la misma tabla de sesiones
    que la vista plana, ya acotada a esa persona).
  - **Categoría** -- opciones calculadas de los propios datos
    (`new Set(sesiones.map(s => s.usuario_rol))`, no una lista fija
    `estudiante/staff/admin` hardcodeada) más "Todas las categorías"; filtra
    el arreglo antes de ordenar/agrupar, así que "Por usuario" con un filtro
    activo solo arma tarjetas para las personas que tengan al menos una
    sesión de esa categoría.
  
  El estado de cada reserva (`confirmada`/`cancelada`/`completada`/
  `no_show`, ver `postgres/init/02-schema.sql`) se pinta con un `Badge` de
  color (`success`/`destructive`/`secondary`/`warning` respectivamente,
  mismo componente `Badge` que ya usa `ServiciosPanel` para el estado
  OK/FALLA de cada servicio).
